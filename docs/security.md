# Security checks and GitHub integration

Security checks run alongside product quality checks. They do not deploy, rotate credentials, publish advisories or enable paid account features. Keep repository/application secrets outside source and pass credentials only to the specific trusted job that needs them.

## Scanner policy

`python3 -m shared_ci.security --config ci/security.json --root . --output evidence/security.json` runs the configured commands, validates tool versions and report schemas, then applies the severity threshold. The reusable `v2-security.yml` calls the same module. Missing tools, malformed reports, scanner errors and expired exceptions fail. A scanner's nonzero findings exit code is accepted only when its report contains valid findings; the final policy still decides pass/fail.

The configuration has `schema: 1`, nonempty `scans`, a `threshold` (`info`, `low`, `medium`, `high`, or `critical`), `max_age_hours` between zero and 168, and optional `exceptions`. Each scan explicitly supplies its command as an argument array, version check, expected version, report format/location and rule/database identity. `{report}` is replaced with a private temporary file path. Never pass a shell command string or credentials in arguments.

| Coverage | Example | Required setup and limits |
| --- | --- | --- |
| Repository secrets | [Gitleaks](../examples/security-gitleaks.json) | Checksum-pinned 8.30.1; full Git history checkout; source redaction enabled. Scanning does not revoke leaked credentials. |
| JavaScript dependencies | [npm audit](../examples/security-npm.json) | Exact npm 10.9.8, committed lockfile; includes development dependencies. Queries the registry advisory service. |
| Python dependencies | [pip-audit](../examples/security-pip.json) | Integrity-locked pip-audit 2.10.0; fully hashed, resolved requirements. Unknown severity blocks until triaged. |
| Filesystem dependencies, infrastructure and secrets | [Trivy](../examples/security-trivy.json) | Checksum-pinned 0.69.3, online advisory DB update, observed DB metadata at most 24 hours old. Scan final container digests separately from the filesystem. |
| Product source rules | [Semgrep](../examples/security-semgrep.json) | Integrity-locked 1.150.0; reviewed local rules and actual SHA256s. Placeholder rule hash intentionally fails. Rule/language coverage depends on the selected rules and edition. |
| Semantic code analysis | [CodeQL policy](../examples/security-codeql.json) | Workflow described below, licensed repository, supported Linux language. |

These examples are starting profiles, not declarations that every product has these manifests. Remove inapplicable profiles with an explicit applicability decision, and add all real manifest directories. Tool installation happens before scanning, from checksum manifests or hash/integrity-locked dependencies. Private registry auditing needs a separately reviewed narrow authentication contract; these public examples receive no registry/provider credentials.

`rules_identity` is either `builtin:<exact tool version>` or a map of local rule files to reviewed SHA256s. The built-in form is only appropriate when the command actually uses the tool's bundled rules; remote/mutable rules must be vendored and checksummed. For npm/pip, `database_identity: online` requires a live advisory query. Gitleaks/Semgrep/SARIF use `none` because they do not use a vulnerability advisory DB. Trivy requires an object with a version-JSON command and DB age bound; the helper checks observed `VulnerabilityDB` metadata after scanning. The Trivy example disables check-bundle downloads and requires a fresh checks cache so it uses version-bound embedded checks; if restoring a cache, run `trivy clean --checks-bundle` during setup first. Tool-controlled caches and external misconfiguration-rule downloads require their own pinning in the product setup; a tool version alone does not authenticate arbitrary remotely selected rules.

Exceptions identify an exact finding `id` and `component`, plus a responsible `owner`, reason and timezone-aware future `expires_at`. They never use global severity suppression. Expired exceptions fail even if the finding has disappeared, so remove obsolete exceptions during review. Receipts contain counts and scanner/rule/DB/policy identity, not source snippets or matched secret values. Preserve only the sanitized receipt. Release evidence must include the actual policy JSON and require a fresh passing security receipt at promotion; old successful CI does not imply current advisory intelligence.

## CodeQL workflow

Call `.github/workflows/v2-codeql.yml` at an immutable shared-library commit. It uses CodeQL Action **v4.39.3 / commit `33d7b85da1a04171e211befe2c739303b9a4c066`**, CodeQL **2.27.4**, and fixed SHA256s for the selected official Linux language bundle. It verifies the downloaded archive before `init` and the installed CLI version afterward. Action tag objects are not used as commit pins.

Required inputs are `config`, one `language`, a unique `artifact-name`, `entitled: true` and `advanced-setup-confirmed: true`. The last two are explicit account/setup attestations by the caller, not automated entitlement detection. Verify licensing and disable existing default setup/duplicate custom CodeQL jobs before adoption; this workflow changes no account settings. CodeQL use on private repositories requires an eligible GitHub Code Security license even if SARIF upload is disabled. [GitHub's CLI licensing documentation](https://docs.github.com/en/enterprise-cloud@latest/code-security/concepts/code-scanning/codeql/codeql-cli) and [default/advanced setup interaction](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/two-codeql-workflows) explain these boundaries.

The Linux language inputs are `actions`, `cpp`, `csharp`, `go`, `java`, `javascript`, `python`, `ruby`, and `rust`. `javascript` covers JavaScript/TypeScript; `java` covers Java/Kotlin only when its build mode can extract the code. This workflow does not provide Swift/macOS, Dart or PHP CodeQL analysis. Flutter still needs Dart analyzer/tests plus dependency/security tools that support Dart. PHP needs its selected PHP/Semgrep/dependency profiles. Apple's native builds/tests remain in Xcode Cloud.

`build-mode: none` is supported for the listed languages except Go. Kotlin files with Java `none` mode are refused to avoid silently omitting them. For compiled projects choose `manual` with a [build configuration](../examples/security-codeql-build.json): explicit compiler version checks and argument-array commands, confined working directory, and bounded timeout. Go, Java/Kotlin and C# manual modes require exact `go-version`, `java-version` (Temurin) or `dotnet-version` inputs and use pinned official setup actions. C++ manual mode uses the preinstalled compiler, whose exact version the product must check; a runner image change fails rather than silently changing compiler. Rust uses `none` in this workflow. There is no implicit autobuild plus a second custom build.

Manual builds preserve CodeQL tracing variables while stripping ambient token/provider credentials; build commands receive no deployment secrets. The compiler and commands must actually cover all product code. Generated code, platform-specific targets, dependency setup and framework support still require a product's coverage review. The job timeout is 60 minutes, each configured command is at most 30 minutes, and process groups are terminated on command timeout. [GitHub's supported build modes](https://docs.github.com/en/code-security/reference/code-scanning/codeql/build-options-for-compiled-languages) describe extraction limits.

The security policy must match the workflow exactly: one scan ID `codeql-<language>-<mode>`, real output `.shared-codeql-results/<language>.sarif`, CLI version `2.27.4` and bundled rules identity. The result directory must be fresh. Analysis runs the pinned `security-extended` suite with the default suite disabled, then **the shared SARIF severity gate** decides the job's verdict. A successful CodeQL command or successful upload is not considered a passing security gate. SARIF security-severity scores take precedence over display-level warnings; missing or unsuccessful analysis reports fail.

By default, `analyze` uses `upload: never` and `upload-database: false`, and only the aggregate receipt is retained. `upload-to-github: true` enables a separate job with `security-events: write` to upload raw SARIF after analysis, including findings that failed the local gate. The caller must grant the required reusable-workflow permissions and confirm its GitHub plan supports code scanning. Fork PRs never enter this upload job; `pull_request_target` never runs analysis. Raw SARIF is retained for one day only when upload was explicitly requested and may contain source locations/snippets. No private provider/API keys are passed to either job.

CodeQL's own default setup is an alternative product decision, not a second required run alongside this workflow. Repository permission/plan limits can affect code scanning, push protection and dependency review. Local scanners remain separate checks; do not report an unavailable GitHub UI integration as enabled.

## Dependency updates and reporting

Copy [dependabot.yml](../templates/dependabot.yml) to `.github/dependabot.yml` and retain only the ecosystems/directories the product actually uses. Configure `develop` as the default branch to keep both security and version update PRs in the feature → develop → staging → main strategy. The template deliberately omits `target-branch`: GitHub security updates always target the default branch, and setting a nondefault target changes how update settings apply. [Dependabot's configuration documentation](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/configure-security-updates) explains that distinction.

Dependency PRs receive normal checks and evidence before merging. The template does not enable auto-merge or promote staging/main. Add private registry secrets only through Dependabot's dedicated secret store and name them explicitly; never embed values in YAML. Dependabot alerts/security updates are enabled in repository settings separately from this file.

Adopt [SECURITY.md](../templates/SECURITY.md) only after the owner selects supported versions and verifies a private report route. Private reporting, advisories, secret push protection, CodeQL upload and branch rules are account/repository capabilities to verify during each product adoption. No new security contact, response SLA, paid license or enabled dashboard setting is assumed.
