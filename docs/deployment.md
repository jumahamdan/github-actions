# Cloud deployment, health, and WordPress contracts

These modules execute supported provider commands against explicitly named targets. Contract tests use synthetic responses; no account has been deployed, credentials created, or provider integration certified by the library tests. Consumer adoption must validate the account's permissions and a staging deployment separately.

Run `python3 -m shared_ci.deploy --root /checkout --config .ci/deploy.json`, `python3 -m shared_ci.health --root /checkout --config .ci/health.json`, or `python3 -m shared_ci.wordpress --root /checkout --config .ci/wordpress.json`. Python 3.11 or newer is required. Successful receipts use `schema: 1` and `status: passed`; WordPress additionally says `packaged_not_published`.

## Workflow and candidate contract

Deployment configuration declares `provider`, `operation`, `environment`, exact `allowed_refs` such as `refs/heads/staging`, `inputs`, `expected_input_digest`, `tools`, `settings`, and optional `working_directory`, `timeout`, and `receipt`. Paths are relative to the checkout root unless explicitly described below. Unknown fields fail. Each CLI tool uses a nonempty argument-array `command`, exact `version`, and optional `version_arguments` (default `--version`). Install the pinned tools and their dependencies before giving the job credentials. Tool installation is a separate workflow concern; example versions are illustrative contract pins, not an instruction to upgrade consumers blindly.

The caller must authenticate the originating successful run and candidate through the evidence module, download the selected immutable artifact, and supply its verified file mapping. `expected_input_digest` is SHA-256 of sorted compact JSON mapping relative input names to their SHA-256 values, matching `quality.input_digest(quality.snapshot(root, inputs))`. The example zero digest deliberately fails until replaced with verified evidence. A self-authored digest alone does not authenticate a candidate. Include every source/configuration/lockfile that can affect a source build and all files in each prebuilt output. Keep credentials, `.git`, caches, generated receipts, and provider-mutated state out of these input selections. Output/config files consumed by an adapter must belong to the selected inputs; changes to selected inputs during execution fail.

Credentialed jobs require GitHub Actions `push` or `workflow_dispatch` on an allowed branch and `DEPLOYMENT_ENVIRONMENT` equal to the declared GitHub environment. The caller must declare that environment, apply its protection policy, and serialize deployments by provider/project/environment. Pull requests and forks never receive publishing credentials. Serialize baseline snapshots with deployment as well. Artifact retention and the evidence manifest connect the module receipt to repository, source, originating run, and release identity; a successful command receipt alone is not promotion authority.

Each command receives only its provider's declared credentials and an isolated temporary HOME/XDG configuration directory. Existing developer CLI logins are not used. Temporary derived access tokens are registered for redaction. Secrets never appear in the JSON examples or command arguments. Provider responses stay in memory; receipts contain identities/fingerprints, not raw configuration or response bodies. Ensure a project's trusted deployment hooks also avoid logging secrets.

| Provider | Explicit credentials and variables | Tools | Result identity |
| --- | --- | --- | --- |
| AWS | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` from the workflow's OIDC role; account/region in JSON | AWS CLI, CDK for stacks | Stack/change-set identity or bucket/artifact/invalidation identity |
| Firebase | `GOOGLE_APPLICATION_CREDENTIALS` pointing outside source/artifacts to workflow-generated ADC credentials; project in JSON | Firebase CLI; Google SDK for function/index verification or access tokens | Function revision, live Hosting release, ruleset, index/field identity |
| Cloudflare | `CLOUDFLARE_API_TOKEN`; account and worker in JSON | Wrangler | Version and active deployment identity |
| Vercel | `VERCEL_TOKEN`; organization/project/target in JSON and matching `.vercel/project.json` | Vercel CLI with environment token support | REST-verified project/deployment identity |
| Netlify | `NETLIFY_AUTH_TOKEN`; site UUID/context/production in JSON | Netlify CLI | Site/deploy identity plus artifact fingerprint |
| Firebase emulators | None; `demo-` project only | Firebase CLI, Java where required, pinned project test runtime | Fresh report with executed passing tests |
| WordPress package | None | Exact pinned PHP when PHP files are selected | Deterministic ZIP SHA-256 and selected-file hashes |

No adapter creates keys, provisions IAM/service accounts, changes GitHub rules, or selects a production promotion automatically. AWS identity must be a temporary assumed role in the configured account. Google SDK receives the exact same ADC path as Firebase. Provider credentials should have only the selected component's required permissions; e.g. rules or Hosting jobs need no Functions deployment grant.

## AWS CDK and static files

[CDK example](../examples/deploy-aws-cdk.json) supports `validate` (synth and read-only template diff) and `deploy`. Both verify AWS account/region and synthesized stack identity. Deployment prepares a CloudFormation change set, inspects its structured operations, then executes that named change set. Removal/replacement of DynamoDB tables, S3 buckets, Cognito pools, KMS keys, and RDS instances/clusters is rejected. Additional `protected_types` extend that set; `protected_logical_ids` reject any operation on selected resources. Unresolved dynamic operations, pagination, and nested stack changes fail closed because their complete effects have not been inspected. A consumer with nested stacks needs a dedicated nested-change-set contract before adoption. Non-replacement modifications still require product review; this is not a universal data-migration proof.

`externally_managed_ssm_parameters` is an explicit list, including an empty list when none exist. The helper reads parameter metadata versions without reading values, rejects synthesized ownership of those names, and verifies versions remain unchanged after deployment. This preserves runtime model/cap overrides separately from deployment defaults. Declare every override the product owns at runtime; this cannot discover undisclosed dashboard settings. Product quota assertions belong in the product tests. CDK bootstrap resources, context lookups, immutable dependency installs, IAM scopes, and approvals remain caller setup.

The [static-site example](../examples/deploy-aws-static.json) requires a prebuilt directory, expected S3 owner, and a CloudFront distribution in the same account referencing that bucket. It runs `s3 sync` with no symlink following, then creates an invalidation and waits for it. Obsolete object deletion requires explicit `delete_obsolete: true`. The receipt records an artifact fingerprint and invalidation ID. This operation is an in-place sync, so readers may see intermediate files; consumers needing atomic switching should use versioned prefixes and a separately reviewed distribution switch. Successful upload/invalidation is followed by application health checks; it is not a full remote byte-by-byte audit.

## Firebase

Separate [Functions](../examples/deploy-firebase-functions.json), [Hosting](../examples/deploy-firebase-hosting.json), [rules](../examples/deploy-firebase-rules.json), and [indexes](../examples/deploy-firebase-indexes.json) contracts allow independent deployment. `components` becomes an explicit CLI `--only` list; nothing silently deploys the whole project. `config` names the real `firebase.json`; source/public/rules/index files must be candidate-bound. Paths inside that provider configuration resolve from its directory.

Functions require `allow_provider_rebuild: true` because Firebase builds their source again. List every expected Gen 2 function name and region; each must expose an ACTIVE revision after deployment. The receipt labels this `same_source_provider_rebuild`. Gen 1 functions need an explicit adapter extension before adoption. Hosting accepts prebuilt `public` output; framework `source` builds and Hosting predeploy hooks are rejected. The configured live channel must have a FINALIZED release; preview releases do not satisfy verification. Hosting/function identities are observed after a serialized operation, not cryptographic assertions about provider build internals.

Rules require release-to-source mappings (`cloud.firestore` or named database, and `firebase.storage/<bucket>`). The active ruleset must belong to the exact project and its source bytes must match the selected file. Index verification compares declared composite fields/query scope and demands READY. Field overrides compare index configuration and optional TTL state through `gcloud firestore indexes fields describe`. Index creation/TTL activation can take longer than deployment; a not-ready result blocks release and must be reverified once the provider finishes. The adapter does not silently treat a pending index as success. Extra remote indexes and removal of obsolete indexes are governed by Firebase's noninteractive deployment semantics; this module verifies requested entries rather than promising destructive synchronization.

[Emulator example](../examples/deploy-firebase-emulators.json) uses operation `emulate`, environment `test`, a `demo-` project, configured emulator ports, and a real `test_command`. Port 3000 is forbidden. `emulators:exec` is the CLI's documented script-string interface, so the validated argument array is encoded with POSIX argument quoting. A prior report is removed; absent, empty, skipped-only, failed, or malformed JUnit/Flutter evidence fails. The caller installs locked test dependencies, Java and emulator binaries ahead of time, and configures nonconflicting ports. No provider credentials are passed to emulator processes.

## Cloudflare, Vercel, and Netlify

The [Cloudflare/OpenNext example](../examples/deploy-cloudflare-opennext.json) deploys the already built worker entrypoint with `--no-bundle`, with a bound `artifact_directory` containing its imported modules. Configured static assets must also be selected inputs. Explicit Wrangler environment/account/worker values must agree. Custom Wrangler build commands are rejected. Build OpenNext and any Worker bundle in the validated build job. `promote` accepts an existing `version_id` and deploys it at 100%; both operations verify the active deployment's version identity. Changes to bindings/migrations remain visible provider configuration and need normal review.

The [Vercel example](../examples/deploy-vercel-prebuilt.json) uses `.vercel/output` produced by the pinned project build and `--prebuilt --archive=tgz`. Preserve the Build Output API files, project linkage and intended build environment together. `build_mode: source` instead requires `allow_rebuild: true` and records `provider_rebuild`. `promote` accepts an existing HTTPS deployment URL and only targets production. Deployment identity is checked through Vercel's authenticated v13 deployment API; no unsupported `inspect --json` flag is assumed. READY and matching project are mandatory. Provider previews/protection and custom environment policy remain project configuration.

The [Netlify example](../examples/deploy-netlify-prebuilt.json) uses explicit site UUID, context, production boolean and built directory. Prebuilt deployment always passes `--no-build` because modern CLI deploy otherwise builds. `build_mode: source` with `allow_rebuild: true` runs the pinned local build first, then deploys its output without a second build; its receipt says `local_rebuild`. Product build source and lockfiles must be part of the selected candidate. Netlify Functions/Edge Functions generated through that build require the consumer's normal Netlify build configuration; the shared contract does not invent a separate serverless bundle.

## Configuration drift and product checks

[Snapshot example](../examples/deploy-config-snapshot.json) executes a real read-only Firebase Remote Config fetch. AWS CDK provider supports `kind: ssm-metadata` and `kind: alarms` with explicit account/region. Operation `snapshot` fingerprints returned JSON and retains no raw settings. Adding `baseline` pointing to the prior receipt makes drift a failure. This is a redacted fingerprint comparison, not a field-level diff or automatic reconciliation. Provider response ordering/metadata may change the fingerprint; review the provider configuration before replacing the approved baseline. SSM snapshots include parameter metadata, not secret values.

The [runtime-test example](../examples/deploy-runtime-checks.json) invokes the existing quality runner against real consumer-owned pytest tests and requires fresh JUnit evidence. Consumers define their actual contract: Cognito authorization/claims, SQS/Firehose delivery and retry behavior, API Gateway responses, DynamoDB persistence, SES/SNS routing, scheduled-job idempotency, and Bedrock model/cap behavior as applicable. The generic example does not create those tests or claim they passed. Mock/service-fixture tests run without credentials. Paid/live Bedrock evaluation belongs to the separate gated AI module; deployments never implicitly invoke it. Public or authorized private HTTP runtime behavior can use health probes. Credentialed business-level integration tests need a separately scoped consumer job rather than ambient secrets added to the quality runner.

## Exact previous-candidate recovery

Recovery uses an explicitly selected previous candidate through the existing operations; there is no generic `rollback` operation in `deploy.py`. The operator first retrieves and authenticates the prior retained candidate and its successful deployment receipt, checks that the current database/configuration remains compatible, and chooses the same exact environment/account/project. Record the current and target candidate/deployment identities in the release's recovery decision. Never infer the prior version from a moving branch or tag.

Use a clean checkout/output directory containing that prior candidate's recorded files and locks. Supply its verified `inputs` mapping digest as `expected_input_digest`, retain the matching library/tool pins, and run the normal adapter with a new unique receipt path. Keep both the prior successful receipt and this recovery receipt linked by their hashes in release evidence; the adapter's returned identity is the observed recovery result, not a claim that an old provider instance was resurrected.

| Provider | Actual recovery call | Important boundary |
| --- | --- | --- |
| AWS CDK | `operation: deploy` using the selected previous source/configuration | Synth/diff/change-set protection runs again. Protected removal/replacement and runtime SSM override changes remain blocked. Compatible code rollback is separate from data restoration. |
| AWS static | `operation: deploy` using the selected previous built directory | Sync and CloudFront invalidation run again. Set obsolete-object deletion only if reviewed; stale files may otherwise remain. It is an in-place publication. |
| Firebase Functions | `operation: deploy`, `components: [functions]`, previous source/locks, `allow_provider_rebuild: true` | Firebase builds that source again. Record the newly observed ACTIVE revision; this is a source redeployment, not byte-identical promotion. |
| Firebase Hosting/rules/indexes | `operation: deploy` with only the chosen prior component files | Verify live release/rules bytes/index readiness again. Reverting rules may reintroduce access defects; reverting index configuration does not restore data. |
| Cloudflare | `operation: promote` with the prior `version_id` and unchanged explicit worker/environment | Require the selected version at 100% in the resulting active deployment. Review binding/schema compatibility before the switch. |
| Vercel | `operation: promote`, `target: production`, selected prior deployment URL | Project/READY identity must match. Promotion does not restore external database or runtime secrets. |
| Netlify | `operation: deploy`, `build_mode: prebuilt`, previous built directory and exact site/context | Creates a new deploy ID from retained output, with `--no-build`; the helper does not call an unimplemented provider restore endpoint. Source mode is an explicit rebuilt recovery instead. |

After the command, run the same configured HTTP/body/header/association, DNS/TLS and product compatibility checks against the recovered target. Link their new receipts to the observed deployment identity and the previous candidate's immutable artifact hashes. A failed recovery or missing health proof remains failed; do not mark it complete merely because the provider accepted an upload. Backup/restore, irreversible migrations, external notification side effects and runtime-secret restoration follow the separately owned product recovery procedure.

## Health verification

[Health example](../examples/deploy-health.json) performs real HTTP GET assertions, DNS resolution and TLS chain/hostname/expiry checks. HTTP supports expected status list, exact response headers, required body fragments and JSON field equality. It refuses redirects, embedded URL credentials, secret-like query parameters and oversized bodies. Optional `header_env` maps an HTTP header to a named existing environment secret; that requires trusted branch context and HTTPS. Bodies and header values are not recorded; receipts retain a response hash, status and host.

DNS can require a subset of IP addresses. TLS uses system trust or a repository-selected `ca_file`, SNI/hostname verification, and configurable minimum remaining lifetime. Private addresses are allowed for an authorized target. Attempts, retry delay, response size and wall-clock duration are bounded, including slow DNS and streaming responses. Check `status`/build JSON against the deployed release when the application exposes identity. Failed or cancelled health evidence cannot establish a successful release.

## WordPress delivery

[Package example](../examples/wordpress-package.json) selects an explicit unique list of regular component files. PHP files receive an exact version check and real `php -l`; HTML fragments require matching explicit tags (optional closing-tag shorthand is deliberately unsupported). This validates syntax/structure, not browser appearance or plugin business behavior. Credentials, `wp-config.php`, environment files, private-key formats and source-control directories are excluded. ZIP contents use sorted names, fixed timestamps/modes and stored bytes for reproducibility. Validation cannot mutate the selected files.

The result is a ZIP/hash and a manual handoff: confirm backup, install through the existing WordPress process, clear cache, verify changed pages/association files, retain evidence and the previous package for rollback. No Hostinger dashboard operation or live WordPress update occurs. Dashboard-only content is outside this package until its separate migration.
