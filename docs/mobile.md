# Mobile candidates and device tests

`python3 -m shared_ci.mobile --config ci/mobile.json --root . --output evidence/mobile.json`

The module prepares pinned dependencies, builds an explicitly authorized emergency Mac archive, compares exported Cloud workflow settings, checks an existing candidate, derives a device-test APK from an existing AAB, or runs an explicitly enabled device test. Success writes `schema: 1, status: passed`; exceptions stop the job. The CLI removes an old receipt before rerunning. It does not build Apple software on GitHub macOS runners, submit an app to a store, or promote a branch. Store processing, tester distribution, and symbol upload are separate operations.

## Apple Cloud setup

Use [run-hook.sh](../scripts/apple/run-hook.sh) as the reviewed loader in a product's `ci_scripts/ci_post_clone.sh` and archive-only `ci_post_xcodebuild.sh`. Vendor the loader itself and record its SHA256 during adoption; its bootstrap trust comes from the reviewed product commit. Set these non-secret variables in the product's Xcode Cloud workflow:

| Variable | Contract |
| --- | --- |
| `SHARED_LIBRARY_REPOSITORY` | Public HTTPS GitHub repository URL |
| `SHARED_LIBRARY_REVISION` | Full immutable 40-character commit |
| `SHARED_PYTHON` | Absolute executable path to the separately provisioned Python interpreter |
| `SHARED_PYTHON_VERSION` | Exact major.minor.patch version; defaults to `3.12.3`, must be at least 3.11 |
| `SHARED_MOBILE_CONFIG` | Product-relative JSON configuration |
| `SHARED_MOBILE_OUTPUT` | Product-relative receipt output |

The loader checks the selected interpreter before Git or network access. An absent executable, Python below 3.11, a partial version or a version different from the exact pin fails with a clear message. It then fetches only the library commit, verifies `HEAD`, disables ambient Git configuration/credential helpers, and cleans the temporary checkout. Its Python dispatcher must also be present at that pinned revision. Python runs with `-I -B`: ambient `PYTHONPATH`, user packages and the working directory cannot shadow the dispatcher, and no bytecode is written into the verified library. The dispatcher inserts its own library path explicitly. Do not put deployment/provider credentials in PR build environments. Apple automatically exposes workflow environment values to its test runners.

Choose and record the interpreter as part of the product's host/image baseline. Before the loader in `ci_post_clone.sh`, provision that exact Python release through the product's reviewed setup mechanism and record the installer/archive checksum and final absolute executable path; on an existing Mac, point to its already verified installation. Set `SHARED_PYTHON_VERSION=3.12.3` and `SHARED_PYTHON` to that installation's actual executable path, then run `"$SHARED_PYTHON" -I -B --version` as baseline evidence. This library does not install Homebrew, select a moving Python release or assume the bundled Xcode Cloud `python3` is suitable. Real Cloud/image provisioning remains an adoption prerequisite; Linux fixture tests prove rejection of unsuitable interpreters, not availability on an Apple image.

For **post-clone**, use [native](../examples/mobile-apple-bootstrap.json) or [Flutter](../examples/mobile-flutter-bootstrap.json) bootstrap configuration. Install the chosen Flutter SDK and Bundler dependencies in a separate pinned setup step first: fetch Flutter's exact commit and verify it, keep `Gemfile.lock`, use Bundler frozen mode, and never select `stable` or install the newest CocoaPods during each build. The helper checks exact Xcode version **and build**, Flutter version **and revision**, CocoaPods version, and all configured lockfile SHA256s before and after resolution. Flutter uses `pub get --enforce-lockfile`, `build ios --release --no-codesign --config-only --no-pub`; CocoaPods uses `bundle exec pod install --deployment`; Swift package resolution uses `-onlyUsePackageVersionsFromResolvedFile -disableAutomaticPackageResolution`. Configure every dependency lock used by the product. It does not rewrite bundle IDs, entitlements, or versions.

For **post-xcodebuild**, the product hook selects this operation only for `CI_XCODEBUILD_ACTION=archive`; other actions need their own test evidence. A failed archive is refused. [Archive verification](../examples/mobile-apple-archive.json) reads only the current `CI_ARCHIVE_PATH`, checks every declared host/widget/watch/complication target, and refuses undeclared app/appex bundles. All targets must carry the expected product version/build, executable, exact specified plist fields, and nonempty dSYMs whose UUID/architecture pairs match the executable. Include companion app IDs, extension point IDs, watch flags, app groups and other capabilities in the product manifest.

When called through this Cloud loader, `apple-verify` and candidate creation accept `"build": "workflow"`. The dispatcher resolves that explicit marker to the current positive-integer `CI_BUILD_NUMBER` in memory, so the next Cloud build does not require a configuration commit. An explicit static build remains unchanged and archive verification still rejects a mismatch. The retained configuration and assurance hash describe the unchanged reviewed template; the inspection and candidate record the resolved actual build. This marker is only a Cloud-dispatch feature: direct module invocation and the emergency Mac recipe keep their explicit build selection.

`signing: signed` additionally requires an authorized branch/start condition, valid `codesign --verify --strict` for each target, and exact signed entitlements equal to the manifest. Debug signing (`get-task-allow: true`) fails. `unsigned` records useful archive evidence but sets `distribution_ready: false`; it cannot prove signing entitlements. The signed flag describes the verified archive, not App Store processing or export readiness. Some Xcode Cloud archives are unsigned and only exported products are distribution-signed; those archives must use unsigned mode and distribution must verify the exported product separately. Do not relabel an unsigned archive as signed.

Apple receipt `application` holds the main app ID/version/build; `source_sha` comes from `CI_COMMIT`. The Xcode Cloud `build_id` is **not** an App Store Connect build resource ID. `artifacts` and `debug_symbols` use paths relative to `CI_ARCHIVE_PATH` (identified by `artifact_root`), so a symbol consumer uses that archive as its root. `archive_sha256` fingerprints a sorted directory manifest of file hashes and confined symlink targets, excluding only reserved `.shared-ci-evidence/`; it is not a zip-file checksum. Payload targets and symbols cannot point into that evidence directory. Store/release candidates must also checksum the actual distributed artifact. Receipts and candidate metadata must be bound to the same source and artifact hashes.

## Same-host Apple dispatch

The reviewed loader now dispatches only `mobile`, `monitoring`, `evidence`, `artifacts`, or `apple_bridge` through `scripts/apple/run-hook.py`. Set `SHARED_APPLE_MODULE` (default `mobile`), `SHARED_APPLE_CONFIG` relative to the source checkout, `SHARED_APPLE_OUTPUT` relative to the selected root, and `SHARED_APPLE_ROOT=source|archive`. Existing `SHARED_MOBILE_CONFIG`/`SHARED_MOBILE_OUTPUT` names remain compatible aliases. `source` is the default and is required for mobile preparation/inspection. `archive` selects only the current `CI_ARCHIVE_PATH` after a successful archive; all output receipts must be under `.shared-ci-evidence/`. An arbitrary directory cannot impersonate the current archive.

The dispatcher verifies actual Darwin/Xcode Cloud execution and exact checkout commit, then binds results to the source checkout even when the artifact root is an xcarchive outside Git. It verifies its library Git revision and clean tree before and after the operation. Candidate creation uses `evidence.create(..., source_root=verified_checkout)` with all retained input/config/check/artifact files still relative to the archive root. Set candidate `library_sha` to `"workflow"` or the exact executing revision; a different caller-supplied revision fails. Verification uses the separate source checkout for both the Git tree comparison and cleanliness check; it never runs Git inside the archive. `SHARED_APPLE_OPERATION=create|verify` selects the evidence operation; artifact dispatch supports packaging only.

Every successful loader invocation prints one compact JSON summary containing `status`, `receipt_path`, `receipt_sha256`, `root`, `library_sha` and `source_sha`. In the reviewed product hook, capture that summary immediately from the successful invocation and build `SHARED_APPLE_CHECK_DIGESTS` as a JSON object mapping each retained candidate check path to its returned SHA256. Candidate creation requires the complete nonempty mapping and compares it to the actual check bytes. Do not recalculate this trusted mapping from arbitrary receipt files after product commands run; the output digest is what prevents a replaced or fabricated receipt from passing. Product hook orchestration and its captured outputs are trusted code, just as reviewed GitHub workflow step wiring is trusted code. This is not an isolation boundary against a malicious native build with host-level access.

Native `apple_bridge` dispatch supports only `apple-export` with the current archive root; GitHub-side import is a separate job. Its optional private S3 bridge uses explicitly scoped existing temporary AWS credentials. Hook-created files are not assumed to appear in Apple's downloadable Cloud artifacts, so durable custom evidence needs that explicit export/import path. Preserve the exact product config bytes with the candidate so typed receipt config hashes remain verifiable. Archive payloads, dSYMs and distribution artifacts stay outside the reserved evidence directory. Native monitoring can now run on this same Apple host with its own scoped existing credentials; its module still validates current build/inspection identity before upload.

This loader does not invent GitHub workflow-run provenance for an Apple build. Archive transport and authenticated Xcode Cloud retrieval must retain Apple's build identity and the selected source; later GitHub operations must use that explicit import contract. A local matching JSON hash alone does not prove provider origin.

## Explicit emergency Mac path

The emergency path is an operator-invoked fallback on an existing authorized Mac, with no GitHub macOS runner and no fake Xcode Cloud variables. Use [archive](../examples/mobile-apple-emergency-archive.json) followed by [inspection](../examples/mobile-apple-emergency-verify.json) configuration. Install the exact reviewed library revision on the Mac first, and use the selected clean product checkout. The config declares operator, reason, source commit, branch ref, unique manual build ID, product version/build and permitted refs. Set `SHARED_APPLE_MANUAL_EVENT=emergency-release` and `SHARED_APPLE_OPERATOR` to that same authorized operator. These markers express an already made manual decision; they do not authenticate a human or authorize the assistant to promote production.

`apple-emergency-archive` refuses Linux, GitHub Actions, Cloud impersonation, wrong source/ref, modified/untracked source and an existing archive destination. Build outputs/receipts must be ignored by the product's Git policy. It performs the pinned native/Flutter bootstrap, runs a real `xcodebuild archive` with selected scheme/configuration/version/build and frozen package resolution, and confirms unchanged source/locks afterward. `signing: unsigned` disables signing; `signed` uses the product's already configured local signing identities/profiles. It does not download profiles, change a keychain, export an IPA or upload a store build. Signing-requested is not distribution-ready: the archive must subsequently pass inspection.

The build receipt records source tree/commit, command fingerprint, toolchain/locks, operator context and payload hash. Pin that receipt's actual SHA-256 in the inspection config's `execution.archive_receipt_sha256`. `apple-verify` requires the same successful build proof and recomputes the archive payload identity before checking every app/watch/widget executable, plist, entitlement and matching dSYM. Signed inspection can be distributable; unsigned inspection stays `distribution_ready: false`. Any ad-hoc re-sign/export step changes payload identity and needs its own truthful signing/export proof; never rewrite the receipt to hide those changes. Retain metadata under `.shared-ci-evidence/` so adding evidence cannot alter the payload identity.

Example sequence (from the product checkout, with the pinned library on `PYTHONPATH`):

```sh
python3 -P -m shared_ci.mobile --config .ci/apple-emergency-archive.json --root . --output .ci-results/emergency-archive.json
# Record the resulting receipt hash in the selected inspection config.
python3 -P -m shared_ci.mobile --config .ci/apple-emergency-verify.json --root . --output .ci-results/emergency-inspection.json
```

The local source remains clean: generate both run-specific build and inspection configuration under the ignored evidence directory rather than editing tracked configuration after selecting its source commit. Retain both the reviewed template and generated config as inputs. Native export/upload stays an explicit product emergency recipe until a corresponding shared provider adapter is selected; a successful archive is never an upload receipt. The public `validate_emergency_context` and `validate_emergency_archive` helpers let same-host monitoring enforce the identical real-Mac/manual/source/build proof.

## Xcode Cloud workflow drift

[Drift configuration](../examples/mobile-apple-workflow-drift.json) compares a complete desired workflow export against a separately obtained actual App Store Connect `ciWorkflows` export. The [desired](../examples/mobile-apple-workflows-desired.json) and [observed](../examples/mobile-apple-workflows-observed.json) fixtures demonstrate the payload shape. Operation `apple-workflow-drift` is read-only and can run on Linux: it makes no Apple API request and changes no workflow.

Workflows are matched by stable resource ID and actions by unique name. The comparison includes enabled/clean flags, project path, scheme/actions/required tests, all start conditions and exact product/repository/Xcode/macOS relationship IDs. Server timestamps, editing-lock state and resource/build-run links are ignored. Missing/extra workflows, changed triggers/toolchain/required-action flags, wrong product, duplicate IDs, unknown attributes, partial relationships and unconsumed pagination fail. Receipts show differing paths and value hashes without copying whole provider configuration. CLI/workflow execution fails on drift while retaining the failure report.

An actual export must be freshly fetched by the authenticated read-only provider integration; fixture comparison alone does not certify live settings or prove Xcode Cloud is active. The helper explicitly records `provider_state_fetched: false`. Provider schema checked against Apple's App Store Connect OpenAPI `CiWorkflow`/`CiAction` resource definitions. Configured test and archive actions still run through Xcode Cloud's own execution engine.

## Build numbers

[Next-build configuration](../examples/mobile-next-build.json) requires a fresh remote-highest document:

```json
{"product":"example-ios","highest":41,"checked_at":"2026-11-15T12:00:00+00:00"}
```

A provider adapter must query the store immediately before allocation; this document is trusted provider evidence, not a request to guess the current number. It expires after five minutes. While holding one product-wide allocator lock, set `MOBILE_BUILD_SERIALIZATION_KEY` to the configured key. The helper locks a persistent local ledger and allocates `max(remote_highest, ledger_highest)+1`, bounded by 2,100,000,000. The ledger also records failed/abandoned allocations: never recycle a number.

A local `flock` or environment variable **cannot coordinate independent cloud workers**. Use one durable allocator host/service, or serialize every workflow that allocates for that product and persist its ledger, including emergency builds. Cross-repository writers need a server-side allocator. For Xcode Cloud's managed counter, configure Apple's next build number above the store maximum and keep competing upload paths under the same allocation authority. This helper computes/verifies a number; it does not update Apple's remote counter or promise that a caller holds a distributed lock.

## Android candidate identity

[Android derivation](../examples/mobile-android-derive.json) takes the already-built AAB, verifies the pinned bundletool JAR checksum/version and configured apksigner version, reads actual package/version/build from `bundletool dump manifest`, and uses `build-apks --mode=universal`. It never runs a second app compilation. The expected keystore file comes from the named environment variable, and passwords go to private mode-0600 temporary files with `--ks-pass=file:` / `--key-pass=file:`. Those files are deleted even on failure. Output is accepted only when exactly one universal APK is produced and `apksigner verify --print-certs` confirms exactly the expected signer. The original AAB hash is checked again before publishing the APK.

Install [bundletool 1.18.3](../examples/tools-bundletool.json) and [Linux Android Build Tools 35.0.0](../examples/tools-android-build-tools-linux-x64.json) before exposing signing credentials. The latter preserves the official runtime layout, including `lib/apksigner.jar`, and creates an `apksigner` launcher on the setup directory's PATH. It does not assume a runner-specific Android SDK directory. Its 61,958,799-byte ZIP matches Google's repository metadata SHA-1 and is locked here by independently calculated SHA-256; the installed `apksigner version` was verified as `0.9`. The safe installer checks the archive hash, path/type/size bounds, and installed runtime integrity. [Google's package metadata](https://dl.google.com/android/repository/repository2-3.xml) is the source of the fixed download URL and package revision.

The example uses `bundletool.jar_env: SHARED_BUNDLETOOL_JAR`, which setup must set to the absolute installed JAR path, normally `$RUNNER_TEMP/shared-ci-tools/bundletool.jar`. It is an explicit file reference, not shell expansion. Absolute regular files outside the product tree are allowed only through this named environment field and still require the configured SHA-256 and version. Symlink paths, missing files, conflicting `jar`/`jar_env`, or changed bytes fail before executing Java. Existing `bundletool.jar` remains a supported repository-relative alternative. `apksigner.command: apksigner` resolves the checksum-installed launcher on PATH. [The credential example](../examples/credentials-android.json) and workflows consistently expose `ANDROID_STORE_PASSWORD`, `ANDROID_KEY_PASSWORD`, and a temporary `ANDROID_KEYSTORE_PATH`; the expected signer fingerprint and key alias remain product-owned.

The upload key's SHA256 fingerprint is non-secret configuration. The keystore path and two passwords are explicit named secrets; no ambient provider credentials are inherited. Run only on the allowed trusted push/manual GitHub refs. Pin Android SDK build-tools by installation path and integrity in tool setup; version text alone is not an installation integrity check. AAB signature verification belongs to the upload adapter: a derived APK's certificate does not prove the source AAB's JAR signature. Google Play App Signing may re-sign the app with another certificate, so this receipt explicitly sets `play_app_signing_verified: false`; later testing from the Play internal track verifies that final installed identity.

## Google device tests

Examples are disabled by default: [Test Lab Robo](../examples/mobile-testlab-robo.json), [DDP instrumentation](../examples/mobile-ddp-instrumentation.json). Set `live_enabled: true` only in a trusted credentialed job. Install **Google Cloud SDK 582.0.0** and, for DDP, its **beta component 2026.08.21** with verified tool setup; this implementation was checked against that SDK's actual command source. Missing beta is refused before execution so `--quiet` cannot trigger an implicit component installation in a credentialed job. Pass a short-lived `GOOGLE_DEVICE_ACCESS_TOKEN` from the product's device-test service account/WIF role. The service account must have access to the selected existing project and results bucket. This helper creates no account/key and never discovers ambient gcloud credentials: it uses a temporary empty HOME/config and a private access-token file, disables usage reporting, and cleans these files.

Test Lab submits `gcloud firebase test android run --type=robo` synchronously with the exact explicit model/version/locale/orientation matrix, result bucket/directory, timeout, and zero flaky retries. Every JSON result must have `outcome: Passed` and the exact expected `axis_value`. Missing, duplicate, extra, failed, flaky, inconclusive, skipped, and unknown outcomes fail. **The helper refuses Test Lab on or after 2027-09-30 UTC.** Migration must be explicit.

DDP Preview submits `gcloud beta device-run sessions submit instrumentation --async --apps=... --test=... --device=... --bucket-name=...`, with one flaky attempt and no parallel flaky retries. SDK 582 async submit has no JSON return value; the helper extracts exactly one session ID from its specific `Creating session [...] in location [...]` status line, then calls `sessions wait` and `sessions describe --full --format=json`. A changed/missing status format fails and requires checking provider jobs before retrying. The full result must identify that session, contain the requested device allocations, and report `DONE` + `PASSED` at session, job and every execution level. Failed waits/result validation trigger a bounded best-effort session cancellation. **There is no DDP Robo fallback.** The product must supply an actual instrumentation APK and adopt its own meaningful test assertions. No passing test-count claim is inferred from a session result.

The device matrix is capped at 20 entries; per-test timeout at 45 minutes; total client deadline at six hours plus up to 30 seconds for DDP cancellation cleanup. DDP's service may retry infrastructure failures even with one flaky attempt; provisioning/queue time, API retries and billing are provider-controlled. Client cancellation cannot guarantee remote cancellation, especially if submission succeeds but the ID cannot be parsed, and Test Lab synchronous timeout may leave a remote job running. Use provider quotas/budgets and inspect remote jobs after interrupted runs. These are execution bounds, not a hard currency cap.

Receipts contain app/test hashes, source commit, exact configuration/device matrix fingerprints, SDK identity, aggregate execution count and results location; no access token or raw app/device logs. Restrict bucket retention and access: device videos/logs can contain user data. Test before distributing to testers; keep results for the exact candidate and rerun when candidate, matrix, test APK, or gate configuration changes.

## Verification and boundaries

`python3 -m unittest discover -s tests -p test_mobile.py -v` covers success and deliberate failures: changed dependencies/toolchain, host/widget/watch identity, entitlements, dSYM UUID mismatch, failed archives, build-number freshness/monotonicity, changed AAB, malformed ZIP/multiple signers, credential cleanup, provider version mismatch, missing/unknown device outcomes, untrusted contexts and Test Lab retirement. These tests use synthetic artifacts and inspected CLI/API contracts. No native app was compiled, signed, submitted or run on a paid device farm during library implementation; adoption must validate the real product's targets, installed toolchain and account permissions.

Primary contracts: [Apple Cloud variables](https://developer.apple.com/documentation/xcode/environment-variable-reference), [Flutter Cloud preparation](https://docs.flutter.dev/deployment/cd), [bundletool](https://developer.android.com/tools/bundletool), [apksigner](https://developer.android.com/tools/apksigner), [Test Lab CLI](https://docs.cloud.google.com/sdk/gcloud/reference/firebase/test/android/run), [DDP instrumentation CLI](https://docs.cloud.google.com/sdk/gcloud/reference/beta/device-run/sessions/submit/instrumentation), [DDP session schema](https://docs.cloud.google.com/developer-device-platform/reference/device-run/rest/v1alpha/projects.locations.sessions), [DDP migration](https://docs.cloud.google.com/developer-device-platform/migrate).
